## 已确认事实清单（TinyEMU + Linux 6.12 启动调试）

### 一、硬件/平台层（TinyEMU 模拟器）

### 七、已解决的问题

35. ~~OpenSBI banner 正常输出后，内核无任何文字输出~~ — 已解决：根因是 `CONFIG_CMDLINE_FORCE=y` 且 CMDLINE 中缺少 `earlycon=sbi`，加入后内核早期输出恢复正常
36. earlycon=sbi 通路已打通：内核 → SBI ecall → OpenSBI → HTIF → TinyEMU 输出
37. ~~内核卡在 `time_init()` / `cpuhp_setup_state()` 不返回~~ — 已解决：根因是 `riscv_machine_get_sleep_duration()` 中 `timecmp = U64_MAX` 时 int64 溢出导致 MIP_MTIP 被错误 set，形成 M-mode timer 中断风暴，CPU 被淹没无法推进。修复为 uint64 无符号比较后，timer 初始化正常通过，initcall 序列恢复推进。
38. ~~内核卡在 `check_unaligned_access_all_cpus`~~ — 已解决（绕过）：根因是 S-mode timer 中断未到达内核导致 jiffies 不递增，`check_unaligned_access()` 中 spin 等待 jiffies 变化的循环死等。将内核配置从 `CONFIG_RISCV_PROBE_UNALIGNED_ACCESS=y` 改为 `CONFIG_RISCV_EMULATED_UNALIGNED_ACCESS=y`，跳过了 jiffies 计时循环。这是绕过而非根因修复，timer 中断链路问题仍然存在。

### 八、时钟源相关备忘

39. CSR time (0xc01) 返回 `insn_counter`（riscv_cpu.c 第 745 行）
40. `rtc_get_time()` 在 `!rtc_real_time` 模式下返回 `riscv_cpu_get_cycles()`，已去掉 `/ RTC_FREQ_DIV`
41. FDT 声明 `timebase-frequency = 10000000`（10MHz），但实际 CSR time 以 `insn_counter` 速率递增，两者是否匹配取决于每秒执行多少条指令
42. 原版 TinyEMU 的 `RTC_FREQ_DIV = 16`，含义是 "CPU 频率 = RTC_FREQ × 16 = 160MHz"，即每 16 条指令 mtime 加 1。去掉除法后变成每条指令 mtime 加 1
43. `riscv_cpu_get_cycles()` 返回值是否等于 `insn_counter` 尚未最终确认

### 十、CLINT / timer 机制备忘

48. 正确的 timer 调用链：内核 SBI ecall 设 timecmp → OpenSBI 写 CLINT mtimecmp → mtime >= mtimecmp 时 CLINT 触发 M-mode timer 中断 → OpenSBI 捕获后设 sip.STIP → 内核收到 S-mode timer 中断
49. TinyEMU CLINT FDT 只声明了 M-mode 中断（IRQ 3 和 IRQ 7），没有 S-mode 的 IRQ 1 和 IRQ 5。在 SBI 委托模型中这是正确的
50. TinyEMU 没有内嵌 SBI 实现，ecall 由 OpenSBI 固件在 M-mode 处理
51. CLINT MMIO 写 timecmp 时会 `riscv_cpu_reset_mip(MIP_MTIP)` 清除 timer pending

### 十二、S-mode timer 中断链路问题（核心待修复）

59. 已确认 S-mode timer 中断未到达内核 — 两个独立症状证实：(a) `check_unaligned_access` 的 jiffies 死等；(b) EXT4 挂载卡住
60. MIP_MTIP 在基本块边界被正确 set（#22），但 OpenSBI 未将其转换为 sip.STIP — 已通过诊断确认
61. 需要追踪完整链路：TinyEMU set MIP_MTIP → raise_interrupt → mtvec 跳转 → OpenSBI M-mode trap handler → set sip.STIP → sret 返回 S-mode → 内核收到 S-mode timer 中断
62. 可能的断点：(a) TinyEMU 的 `raise_interrupt` 逻辑在 M-mode 下是否正确触发 trap；(b) OpenSBI 的 timer trap handler 是否正确处理；(c) mideleg 是否正确配置（STIP 应该被委托给 S-mode）

### 十三、OpenSBI trap handler 诊断结果（关键发现）

63. OpenSBI trap handler 入口地址：`0x800003c8`（direct mode，mtvec 低位 = 0）
64. 每次 M-mode timer 中断 trap 到 `0x800003c8`，执行约 177 条指令后 mret 回到 `0x803b5aee`（S-mode 的 WFI 处）
65. `mie` 始终为 `0x2a8`（MTIE=1），从未被清除 — 证明 `sbi_timer_process()` 中的 `csr_clear(CSR_MIE, MIP_MTIP)` 从未执行
66. `mip` 始终为 `0x80`（MIP_MTIP），从未被转换为 MIP_STIP — 证明 `csr_set(CSR_MIP, MIP_STIP)` 也从未执行
67. OpenSBI 的 C 函数 `sbi_trap_handler()` **确实被调用了** — 通过 CSR 0x342（mcause）读取诊断确认，读到的值为 `0x8000000000000007`（M-mode timer interrupt），完全正确
68. `sbi_trap_handler` 读了 mcause 后，应走 `mcause & MCAUSE_IRQ_MASK` → `sbi_trap_nonaia_irq(7)` → `case IRQ_M_TIMER` → `sbi_timer_process()`
69. 但 mip 没被写（没有 `mip_write` 输出），mie 也没被写 — 说明 `sbi_timer_process()` 没被执行到
70. 问题定位在 `sbi_trap_handler()` 内部分发逻辑到 `sbi_timer_process()` 之间的某个环节
